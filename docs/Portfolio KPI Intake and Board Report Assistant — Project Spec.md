# Portfolio KPI Intake and Board Report Assistant — Project Spec

Nov 4, 2026 · @Swayam Shree

## Overview

The tool takes messy monthly KPI spreadsheets from portfolio companies, turns them into one validated table, calculates the SaaS metrics investors track, and drafts board commentary in which every number links back to its source file and cell. Anything that doesn't reconcile goes to a review list for a person to decide, instead of being guessed.

**30-second pitch:** "Every month, each portfolio company sends KPIs in its own format. Someone has to clean them, check them, and write the board update. I built a workflow that does the cleaning and checking in code, uses Claude only where judgment helps, and never lets a number into the report unless it traces back to a source cell. On my test set it caught every planted error."

## Problem and users

At a software-focused private equity firm, each portfolio company's finance team sends monthly or quarterly KPIs. Formats differ by company: different labels, units, layouts, and missing or corrected figures. Before anyone can compare companies or prepare a board meeting, an analyst cleans and checks the files by hand.

| User | What they need | What the tool gives them |
| --- | --- | --- |
| Portfolio reporting analyst | Clean, comparable numbers without hours of spreadsheet work | One standard table plus a list of exactly what needs checking |
| Deal lead or investor | A trustworthy read on how each company is doing | Board commentary with every figure traceable to its source |
| Portfolio company CFO | Fewer follow-up emails about their file | Specific questions ("May ARR doesn't reconcile") instead of vague ones |

**Why it fits K1:** the AI Intern posting names "board-report generators," "data pipelines," and "agentic workflows" that "replace manual work across the firm and its portfolio companies." K1 has invested in 275+ software companies, so a repeatable intake process saves time on every one of them.

## Scope

The MVP handles one month-end cycle for five fictional companies, end to end, from upload to draft report.

**In the MVP**

- Read Excel and CSV files in different layouts (months as columns or as rows, different header rows)
- Map each file's labels to one standard set of metrics
- Convert units ($K vs. $M, 0.81 vs. 81%) and remove duplicate files
- Run consistency checks and send failures to a review list with file and cell
- Calculate ARR growth, net and gross retention, churn, gross margin, ARR per employee
- Claude drafts per-company and portfolio commentary from validated numbers only
- Streamlit dashboard: upload → clean table → review queue → draft report → export; uploading starts the whole pipeline
- Score the pipeline against an answer key of planted errors

**Stretch, if time allows**

- Trend charts of each company's ARR and retention on the dashboard
- A per-company list of follow-up questions, ready to send to its CFO

**Out of scope**

- Real company data, login, a database, cloud deployment
- Email or cloud-folder intake (the dashboard upload is the single entry point)
- Microsoft 365 integration (designed for, not built)
- Forecasting or valuation

## Test data

The test files are already prepared and are not generated by this project: five fictional companies with 12 months of data each, each in a different spreadsheet layout with specific planted errors, plus an answer key. They go in `data/raw/`. Say in the demo that the data is fictional and why: real portfolio submissions are private.

**Realistic ranges for small software companies:** ARR $10–80M, gross margin 75–85%, net revenue retention 95–115%, monthly churn 0.3–1.5% of ARR. Revenue is about ARR ÷ 12 plus a little services revenue.

| Company (fictional) | File style | Planted errors |
| --- | --- | --- |
| Ridgeline Field Software | Clean, months as columns, $K | None (the control case) |
| Harborview Compliance | Months as columns, $M, different labels, GM as a decimal | Missing month; one ending ARR that doesn't match its rollforward |
| Northpass Health IT | Months as rows, header on row 4 under a logo block | Resubmitted duplicate file with one changed figure |
| Cobalt Facilities | One tab per quarter | Beginning ARR doesn't equal prior month's ending ARR |

The answer key (`answer_key.json`) lists each planted error with company, month, metric, and error type, so the evaluation is automatic.

## Architecture

&#91;embedded content: KPI pipeline · 8 steps, 2 that call Claude, 1 review loop\]

Files move left to right through ingest and mapping into one standard table, then right to left through checks, metrics, and commentary to a draft a person approves. Values that fail a check wait in the review list until someone resolves them; only then do they reach the metrics.

## Standard schema and label matching

Calculations never read a file's own labels. Every file is converted to one long table with a fixed set of metric names:

```
beginning_arr, new_arr, expansion_arr, contraction_arr, churned_arr, ending_arr,
revenue, gross_margin_pct, customers, headcount
```

| company | month | metric | value\_usd\_k | source\_file | source\_cell |
| --- | --- | --- | --- | --- | --- |
| Harborview Compliance | 2026-05 | ending\_arr | 12920 | Harborview metrics FINAL v2.xlsx | F2 |

Labels are matched in three layers, cheapest and most predictable first:

1. **Lookup table** (`aliases.yaml`): known names for each metric, matched after lowercasing and removing units and punctuation.
2. **Fuzzy match** with `rapidfuzz` for small variations and typos, above a set similarity score.
3. **Claude** for anything still unmatched: it gets the label, sample values, and the list of standard names, and returns a structured guess plus a confidence. The guess goes to the review list; once a person confirms it, it's added to the lookup table, so the next file with that label needs no review.

Layout rules run on every file: find the header row by looking for month-like values, flip months-as-columns into rows, read units from headers or notes, scale 0–1 percentages to 0–100, and keep the newest of any duplicate company-month file while flagging it.

## Validation checks and metrics

Checks run on every company-month after conversion; a failure sends that value to the review list with its file, cell, and the reason.

| Check | Rule | Catches |
| --- | --- | --- |
| ARR rollforward | beginning + new + expansion − contraction − churned = ending, within $1K | Typos, wrong totals |
| Month-to-month continuity | this month's beginning ARR = last month's ending ARR | Restated or pasted-over figures |
| Completeness | every month present for every required metric | Missing months |
| Plausible ranges | gross margin 0–100%, customers and headcount > 0, churn ≤ 0 in the sign convention | Impossible values, unit mistakes |
| Duplicates | one file per company-month | Resubmitted files |
| Unit sanity | ARR within 10× of the company's own median | $K vs. $M mix-ups |

Metrics are calculated in plain Python, only from rows that passed every check:

| Metric | Formula |
| --- | --- |
| ARR growth (MoM, YoY) | ending ARR ÷ ending ARR one month (or 12 months) earlier − 1 |
| Net revenue retention (12-mo) | (starting ARR + expansion − contraction − churn over 12 months) ÷ starting ARR |
| Gross revenue retention | (starting ARR − contraction − churn) ÷ starting ARR |
| Monthly churn rate | churned ARR ÷ beginning ARR |
| Gross margin | as reported, normalized to a percentage |
| ARR per employee | ending ARR ÷ headcount |

With only 12 months of data, 12-month retention covers one window per company; that limitation is stated in the report.

## Claude's role and guardrails

Claude does two jobs: matching labels that code can't, and writing commentary. It never calculates or changes a number.

**Commentary generation**

- Input is only the validated metrics table, each value with an ID (for example `harborview.2026-06.nrr`), plus the open review items.
- Claude returns structured output: paragraphs with figures written as references like `{harborview.2026-06.nrr}`, not typed numbers.
- Code replaces each reference with the formatted value and a link to its source file and cell.
- A check scans the final text for any number that didn't come from a reference. If one is found, the draft is rejected and regenerated.
- Open review items appear as open questions ("Harborview May ARR is under review"), never as facts.

**Other guardrails**

- File contents are treated as data, not instructions. Cell text like "ignore previous instructions" is passed as a quoted value and included in the test set.
- Every Claude call is logged with its input, output, and model version, so any draft can be traced.
- A person approves the draft before it goes anywhere.

This is the answer to "how do you stop the AI from making up numbers?": it can't write one, and if it tries, code catches it.

## Dashboard

One Streamlit dashboard is the single entry point: uploading files runs the whole pipeline, and every step a person takes happens on the same screen.

| Page | What it shows | What the user does |
| --- | --- | --- |
| Upload | Drop zone for Excel and CSV files, reporting-month picker, processing progress | Upload the month's files; the pipeline runs automatically |
| Portfolio overview | One row per company: ending ARR, ARR growth, net retention, churn, gross margin, and a status (ready or needs review) | See which companies need attention |
| Review queue | Each flag with company, metric, file, cell, the reason, and Claude's suggested label match where relevant | Accept a correction, confirm or reject a label match, or mark it as a question for the company |
| Board draft | Commentary with every figure linked to its source cell; open review items listed as questions | Edit, approve, export to Word |

Resolving a review item reruns checks and metrics for that company, so the overview and the draft update right away.

**At K1:** the pipeline has one entry point (`pipeline/run.py`), so a SharePoint library with a Power Automate trigger could call it alongside the upload page, with approvals and alerts in Teams. Notifications sit behind a small `Notifier` interface, so adding Teams means one new class and no change to the processing code.

**Production concerns to mention:** the same file uploaded twice is processed once (matched by file hash); every run is saved with its inputs, flags, and decisions, so an approved draft can be traced; access would be limited per company.

| Language | Python 3.11+ | pandas for tables, fast to write |

## Evaluation and success measures

`eval/score.py` compares the review list to the answer key and reports results the way you'd report a classifier.

| Measure | Target for the demo |
| --- | --- |
| Planted errors caught (recall) | All of them |
| False flags on clean data (Ridgeline) | Zero |
| Labels mapped correctly | All; unknown labels go to review, not a silent guess |
| Numbers in the draft that trace to a source cell | 100% |
| Made-up number caught by the check | Shown live with a deliberately bad draft |
| Prompt-injection cell treated as data | Yes |
| Time to process 5 files | Measure and report it |

**Business measure to state carefully:** time saved. Estimate the manual baseline honestly ("cleaning and checking five files by hand takes roughly a few hours") and label it an estimate, not a measured result. At K1, the real measures would be analyst time per cycle, errors reaching a board deck, and whether people keep using it.

## Build plan

The core takes about 3 hours; plan for about 4 with debugging. Stop at the end of the core if it works end to end, then add stretch items. The test files are already prepared, so the build starts at ingest.

**Core**

1. **0:00–1:00 Ingest and mapping.** Header detection, reshaping, units, alias table, fuzzy match, Claude fallback with review.
2. **1:00–1:30 Checks and metrics.** Validation rules, review list, metric calculations, a few pytest tests.
3. **1:30–2:15 Commentary.** Claude draft with figure references, the number check, review items as open questions.
4. **2:15–3:00 Dashboard.** Streamlit pages for upload, portfolio overview, review queue, and board draft with export.

- Per-company follow-up questions for each CFO

## Demo script and talking points

Keep the live demo to about 3 minutes, then let them ask questions.

1. **Set up (20 sec).** "These are five fictional portfolio companies. Real submissions are private, so I built test data with the problems finance teams actually send."
2. **Upload (20 sec).** Drop the five files into the dashboard's upload page; the pipeline runs on its own. Show one clean file and one messy one side by side.
3. **Review list (60 sec).** Show the flags: Harborview's May ARR doesn't reconcile, Northpass sent a duplicate, Verity reported 112% gross margin. Show the score against the answer key.
4. **Board draft (60 sec).** Click a number in the commentary and show the source file and cell. Show a flagged item appearing as an open question, not a fact.
5. **Guardrail (20 sec).** Run a deliberately bad draft with a made-up number and show the check rejecting it.
6. **Close (20 sec).** "With K1's data, the next step is a SharePoint trigger through Power Automate and a finance sign-off before anything reaches a board."

**Questions to be ready for**

- *Why not let Claude do the math?* Calculations need to be exact and repeatable; the model writes words, code does numbers.
- *What if a company changes its format?* Layout rules handle most changes; new labels go to review once and are then learned.
- *Why a workflow and not an agent?* Fixed steps make board numbers predictable; an agent choosing its own steps would add unpredictability with no benefit here.
- *How would you know it's working at K1?* Analyst time per reporting cycle, errors reaching board decks, and continued use.
- *Did you consider buying instead of building?* K1 owns Board Intelligence, which already helps with board reporting; check what it covers before building more.

## Limitations and next steps

State these yourself before anyone asks; it reads as judgment, not weakness.

**Limitations**

- Test data is fictional; real files will have problems not in the test set.
- Metric definitions (what counts as ARR, how churn is timed) are assumed and would need to be agreed with K1's finance team.
- Twelve months of data gives one 12-month retention window per company.
- Label matching covers the alias list built so far; a very different file still needs a person's review the first time.
- No access control, which real portfolio data would require (per-company permissions).
